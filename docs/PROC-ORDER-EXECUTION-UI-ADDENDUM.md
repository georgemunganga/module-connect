# PROC — Order execution review UI

Status: Source authored; not compiled, browser tested, deployed or enabled by this increment.
Backend reference: ERP `2f97a46`, additive execution-read contract. UI base `d7de3cc`.

1. **Feature identification:** Procurement → Purchasing → Order execution review → Discover, inspect, record Finance evidence, submit, authorise sending, record dispatch evidence, recover uncertain outcome.
2. **Purpose and business outcome:** Finance and dispatch staff can find orders within their existing responsibilities without receiving general PO read/ownership grants.
3. **Scope and exclusions:** Existing order pages and shared controls. Approved-source conversion and linked unfunded draft editing are included; assigned PO approval decision UI remains a separate prerequisite. No ledger posting, payment, automatic vendor dispatch or invented receipt.
4. **Parent and related features:** Approved PR source allocation, PO commercial workflow, Core identity/permissions/branch scope, Finance evidence, supplier delivery evidence.
5. **Actors and participants:** Buyer, independent Finance verifier, independent dispatch verifier. Server resolves current canonical identity and worker independence.
6. **Entry points and triggers:** Existing Purchase Orders link, role-based buyer/Finance/sending tabs, order detail links. No new sidebar.
7. **Preconditions:** Live mode, actual ERP context/meta and `capabilities.orders=true`. Matching migrated backend and approved server policies. `orders=false` retains legacy draft screens; both order capabilities false stay gated.
8. **Workflow:** Select worklist → review exact order/lines/history → open an eligible evidence/command form → explicitly attest review → POST one keyed command → refresh current authoritative detail. On uncertain result, preserve payload/key and query the scoped receipt before another action.
9. **Status and state transitions:** Display actual Draft/PendingApproval/Approved/Returned/Rejected/IssuePending/Issued state. Submit/Issue commands pin expected order version; Finance/dispatch evidence use current revision/source/issued references. Server alone changes state. Failed/unknown dispatch does not imply delivered.
10. **Permissions and data scope:** Buyer list requires `procurement-po-read`; Finance list `procurement-po-finance-confirm`; dispatch list `procurement-po-dispatch-confirm`. All requests carry existing Core company/branch headers and credentials. Candidate permission must also be present before showing its form. Direct URL/server authorization remains final.
11. **Business rules:** `actionCandidates` only permit opening forms; never promise an approved command. Evidence must be independently verified under an approved server policy. UI cannot enable a missing policy. Existing unlinked draft create/edit is replaced with approved-source conversion and linked-only editing when order execution is enabled. Creation pins exact source request versions and one-to-one line indexes; mixed branch/currency grouping is blocked for usability while the server rechecks eligibility. Edit preserves all line IDs, unit/currency and metadata and offers no source/line replacement.
12. **Data fields and ownership:** Procurement owns order/source/submission/issued/evidence records. Core owns identity and scope; Finance owns the external reservation/commitment decision. Amounts and quantities from execution APIs remain exact decimal strings. Validated money tokens are emitted as raw JSON numbers for existing decimal-bound server command DTOs, without Number conversion.
13. **Screens and data views:** Existing list layout, shared tabs/filter/table, scoped paging, detail/line totals, Finance evidence, approval history and sending history. Evidence forms reuse shared Modal/Input/Select/Switch/Textarea.
14. **User experience and human behaviour:** Plain labels and explicit evidence attestation. Loading/empty/denied/error states; old detail is removed on identity/order navigation and stale async callbacks are ignored. Sending authorization and actual vendor delivery are distinct.
15. **Notifications and communications:** Existing backend transaction/outbox owns notifications. UI success only reports returned server state; no independent notification send.
16. **Documents and attachments:** Records evidence references only; no new upload/storage service or supplier attachment permissions.
17. **Exceptions and edge cases:** Nonexact numeric response amounts fail closed. Blocked/unknown hints cannot execute. Known guard conflicts refresh detail and clear old action form. Transport/5xx/timeout/invalid success responses remain unconfirmed; never automatically repeat a write.
18. **Integrations / APIs / events / sandbox:** GET execution-worklist with view/page/status; GET execution-detail; GET approved-sources; POST Convert with raw exact decimal line fields; PUT SourceEdit with version/reason and fixed line IDs; POST Finance/DraftFinanceRelease/FinanceRelease/Submit/Issue/Delivery commands; GET actor-owned command receipt. Backend validates exact amount, complete sources, policy, scope, worker independence and versions. Mock browser tests are not actual API acceptance.
19. **Audit / security / privacy:** Server retains audit/receipts; no frontend audit substitute. Unconfirmed command memory is scoped by company/branch/canonical worker/order and survives SPA detail navigation. It is not persisted to disk and does not survive a full reload; the screen tells users to retain the key and keep the tab open. Never automatic replay or broad permission grant.
20. **Reports / dashboards / metrics:** Purpose-specific bounded worklist counts only; no new KPI definitions or cross-scope totals.
21. **Configuration and localization:** Company currency comes from actual order/context. Server supplies allowed delivery channels. Existing branding/fonts/shared components remain unchanged. Timestamp inputs preserve milliseconds and user chosen local time.
22. **Non-functional requirements:** Abort stale reads, ignore detached callbacks, one mutation at a time, bounded paging. Keyboard-accessible shared controls, readable exact financial values and responsive table scroll.
23. **Postconditions:** A confirmed command shows the current server detail; reconciliation explicitly distinguishes recorded historical outcome from current state and says replay is not authorised by the receipt.
24. **Failure and recovery:** Original UUID/body retained unchanged in browser memory while unconfirmed. Check saved result makes only GET. Matching actor/scoped receipt resolves uncertainty; unavailable receipt leaves new actions blocked. No forced reset or new key after ambiguous write. Reopening/refetching cannot grant an action.
25. **Acceptance criteria:** Narrow Finance/dispatch discovery without general PO read; exact totals and payloads; current hint/permission gating; stable uncertain command; no duplicate POST during reconciliation; no stale detail after denied navigation; execution flag preserves legacy behavior; unlinked draft bypass blocked.
26. **Test scenarios:** Focused mocked browser suite covers Finance/dispatch discovery, exact lost-response recovery, issued/version/channel bindings, 409 refresh, 403/404 detail navigation, blocked hints, legacy false capability, fully disabled gate, unlinked editor block, malformed money, buyer submit/issue and both Finance release routes. Additional source tests cover one/multiple sources, exact partial quantities, immutable line mappings, mixed branch denial, 409/403, unknown-target conversion receipt recovery, edit-only metadata preservation and uncertain update recovery. Existing draft suite must also pass. Actual backend/browser proof remains a separate gate.
27. **Ownership and dependencies:** UI uses module adapters plus shared ERP components/shell. Backend owns authorization, relational source controls, policy and atomic evidence/receipt persistence. Root controls resource scheduling, migration/release and capability activation.
28. **Open decisions and assumptions:** Assigned PO decision UI remains a future adapter. Execution-detail does not expose current approved source availability/price ceilings, and edit-only users need not have Convert permission; editing therefore honestly states that limits are checked by the server on save. A narrow additional scoped sourceAvailability projection is a follow-up, not a fabricated maximum. Conversion receipt recovery supports an initially unknown target order ID; no POST retry occurs before receipt reconciliation. Browser-memory recovery is temporary; cross-reload/operator recovery would need a separately reviewed safe persistence/user journey. No release until TypeScript/build, focused/legacy browser gates and actual migrated API workflow acceptance are recorded.
