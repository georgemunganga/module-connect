# Original invoice decimal precision — frontend candidate

Status: Source authored, not built/tested/deployed. Isolated branch from39052e5; existing frozen invoice bundle/worktree not changed.

The original intake editor previously coerced quantities/rates/tax through JavaScript Number, then parsed original18,4 response numbers using response.json. The browser could change12345678901234.5678 into12345678901234.568 before the backend's valid18,4 boundary saw it.

`InvoiceLineInput`, original detail and summary financial fields now use decimal strings. Shared existing Input/layout/buttons are reused; decimal text fields retain their entered digits without Number conversion. Submission canonicalizes and validates18,4 lines and aggregate headers before any fetch. Prices/quantities use exact BigInt scaled4; individual products accumulate at scale8, then tax lifted from4 to8. No per-line product rounding/rejection is introduced: two8dp products may aggregate to a valid4dp header. The backend remains authoritative. Invalid/partial input has no invented zero total; preview retains significant8dp derived digits, server-compatible originals retain up to4dp. Formatting groups digits and preserves significant digits with at least2fraction places, without financial Number/toFixed.

The backend's existing numeric response wire is unchanged. A bounded proper JSON token reader (2MiB UTF8, depth24,25,000 nodes) identifies only known original financial property values and quotes/canonicalizes their numeric lexemes before JSON.parse. It traverses object/array/string/escape/literal/number syntax; it never regex-replaces whole JSON or money-like text inside descriptions, names or filenames. Escaped property names and duplicate decoded names are handled structurally. Unsupported/nonrepresentable values fail closed. Nonfinancial metadata retains ordinary number types. The same request helper continues binary document downloads unchanged.

The source base contains existing exact order decimal string validators/encoders, but no reusable BigInt arithmetic/JSON numeric-lexeme reader. New small invoice helpers provide this actual missing behavior without changing the existing order contract or adding a decimal library.

Authored unit/client cases cover numeric wide4dp originals, exact string POST, raw escaped descriptions, grouped display, exponent lexemes, malformed/injected/ambiguous JSON, oversized/deep input, metadata types, already-rounded numeric inputs denied before fetch, unrepresentable headers and valid8dp products whose sum fits4dp. Existing intake mocks now aggregate string inputs exactly. A separate mock-transport wide-value browser case asserts raw numeric response→unrounded UI and exact outbound strings. Existing2actual P26 cases/one-record manifest remain unchanged. No production financial owner, payment action, backend field/model/schema or fixture count change is introduced.

Required next gates: source review, focused exact helper/client tests and existing invoice tests, TypeScript, new isolated candidate build, scoped mock-browser tests and the existing2actual P26 cases plus owner verifier on the new bundle. All are pending; no Node/build/browser jobs were run for this source checkpoint.
